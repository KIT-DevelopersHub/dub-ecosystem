# 開発の進め方・レビュー方法(Commander 専用)

> 個人 config の開発規約 skill(dev-workflow / pr-delivery / multi-review / subagent-ops)の
> うち「開発のやり方」に当たる部分だけを複製。秘書運用(判断キュー/起票/送る)は除外。

## 標準フロー(計画 → 実装 → push → PR)

1. **計画**: 3手以上 or 設計判断を含むなら計画から。全体計画 → 個別実装計画。
2. **実装**: Simplicity First / Minimal Impact。必要な箇所だけ変更する。
3. **セルフレビュー**: 各フェーズ切り替わりで実施(下記)。
4. **push → PR**: コミット規約(件名 ~50 行目安)・PR 規約(差分は小さく ~200 行目安・大きければ
   タスク毎に分割し統合 PR で束ねる)。PR は作者インライン自己レビューでレビュアーに端的に伝える。
5. **エレガンスチェック / 完了報告前チェック**: 型・ビルド・テスト green を裏取りしてから完了。

## セルフレビュー(多角レビュー)

- **発火**: 全体計画後・個別実装計画後・各コミット前・PR 完成時。
- **最低 2〜3 人格**。観点: DB 変更・認可・分散整合性・SRE・TypeScript/React・
  **UI 変更はプロダクトデザイナー視点を必ず含める**。スクラム 3 役(SM/PM/Tech Lead)も。
- レビュータグ: `[must]`(必須) / `[nits]`(些細) / `[imo]`(意見) / `[suggestion]` /
  `[Q]`(質問) / `[LGTM]`。指摘には必ず推奨案と理由を添える。

## サブエージェント運用(並行開発)

- **並行エージェントは必ず worktree isolation**(共有 WD での同時 `git checkout` はブランチ
  混入・コミット汚染を起こす)。別リポで並行させる時は `git worktree add` で独立ディレクトリを作る。
- **開発系タスクはマルチエージェントを基本**: 実装と別視点の検証(発見役 + 反証役/レビュー人格)を
  並行させ品質を上げる。独立に分解できる作業は複数 Agent へ同時ファンアウト。
- 委譲は短冊化・時間箱(目安 5 分/実ブラウザ検証は別工程で非同期)。1 エージェントに全工程を詰め込み
  長時間化させない。E2E は実装と同期で回さず完成後に別工程で非同期に。
- **非力 PC 制約**: 重いサーバー/LLM の同時多重起動をしない。mass rm をビルド中のツリーと並行しない。

## Dub レビューコメントの体裁

- タグ文頭・改行/太字/絵文字(:pray: 等)・Quote/Code/List を活用して読みやすく。

## イエスマンにならない

- 設計・数値・前提に矛盾やリスクを見つけたら遠慮なく指摘する。指摘には必ず推奨案と理由を添える。
- 知らない事実は憶測で埋めず、先にユーザーに確認する。
